# 复用本机咚咚会话完成 AI 云平台登录

验证日期：2026-09-11。对象：本机 macOS、咚咚 3.4.0、当前用户自己的有效会话。

## 结论

已通过真实接口验证完整链路：读取本机咚咚现有会话 → 获取临时票据 → 换取 AI 云平台登录态 → 成功查询个人额度。

本次没有使用 OAuth 回调、工作台应用登记或密码登录，也没有改写咚咚配置。无需上述回调配置即可完成本次链路；这不能推广为所有版本、账户和组织均已验证。

已接入当前 Tauri 产品代码（`rust-desktop`）：Rust 负责本地读取、解密、会话交换和额度查询，共享设置页与托盘提供自动 / 手动两种入口。早期独立验证使用 Node；产品实现不需要捆绑 Node，也不依赖咚咚运行时 IPC、页面注入或浏览器 Cookie。根目录的历史 Electron 版本未同步这一功能。

## 本机存储证据

- 文件：`~/Library/Application Support/emc/emc.config.v3.json`。
- 保存者：咚咚安装包的 `seagull/main/dist/index.cjs`，通过 `electron-store` 保存 `loginInfo`。
- 当前配置中存在 `token`、`badgeId`、`uniqueKey`、`deviceNumber` 等字段。本次请求仅使用现有会话相关字段，没有使用保存的密码。
- 加密实现来自安装包内 `conf/dist/source/index.js`：带随机 IV 的 AES-256-CBC，PBKDF2 派生密钥。应用侧提供的解密参数在安装包中，本次没有调用系统钥匙串解密。
- 解密只在验证进程内存进行，没有输出解密后的配置、身份字段值、密码、会话 token 或临时票据。
- 请求结束后重新读取原文件并进行字节比较，确认配置内容未变。

实现时只投影所需的会话字段，不保留其他配置。解密过程不可避免会在内存中接触整个配置文件，但不应序列化、转存或记录其中的其他内容。

## 实际请求链路

### 1. 用现有咚咚会话生成临时票据

`POST https://dongdong-api.eastmoney.com/chatserver/app/api/tokenAuth/newTempToken`

按照客户端 `setAuthInfo` 的实现发送 `token`、`X-Job-Number`、`X-Unique-Key`、`Device-Info`。设备信息使用当前系统和客户端版本，`sessionType` 为 `PC`。

结果：HTTP 200，业务码 `200`，获得非空 `data.tempToken`。

源码：`use-page-CZ_j27QQ.js` 中的 `getTempToken()`、`index-BRXEqGCB.js` 中的 `chatServer` getter、`setAuthInfo()` 和 `onResponseOK()`。最后一个函数会将业务响应的 `data` 解包，因此直接发 HTTP 请求时必须读取原始响应的 `data.tempToken`。

### 2. 换取 AI 云平台会话

`GET https://aihub.eastmoney.com/ai-cloud-hub/api/v1/auth/dongdong-token`

查询参数为 `ddSource=group`、`sessionType=PC`、`oa_token=<临时票据>`；请求头携带新生成的 `X-Dong-Client: WEB-<UUID>`。`group` 来自当前咚咚应用版本的来源映射，不应在跨组织实现中写死。

结果：HTTP 200，取得包含 `userId`、`token`、`expireAt`、`user` 的平台会话。本次仅在内存中持有，未保存。

源码：AI 云平台线上 `admin-core-BUI31b0W.js` 中的 `dongdong-token` 调用及请求拦截器。

### 3. 查询个人额度

`GET https://aihub.eastmoney.com/ai-cloud-hub/coding-plan/usage`

携带平台会话的 `X-Dong-Auth`、`X-Dong-User` 和步骤 2 使用的同一个 `X-Dong-Client`。

结果：HTTP 200，业务码 `000200`；额度上限和已用额度均可解析为有效非负数，额度上限大于零，并有费用更新时间。本次两个金额字段实际为字符串，需按现有共享额度逻辑进行规范化。报告不记录账户身份或额度金额。

本次没有收到 `x-dong-refresh` 响应头。线上脚本存在相应刷新分支，但此次没有触发或验证它。

## 已实现的登录流程

| 情况 | 行为 |
| --- | --- |
| 首次安装，无已保存的账户 | 默认尝试使用本机咚咚账户 |
| 从已有手动登录的 Tauri 版本升级 | 迁移原凭据，保留手动模式 |
| 设置 / 托盘选择“使用咚咚账户” | 清除旧账户、旧额度和旧请求，读取咚咚并连接 |
| 选择“手动登录其他账户” | 使用独立的官方登录窗口；手动模式保留到下次启动，不被咚咚覆盖 |
| 主动退出账户 | 清除平台凭据，持久化暂停自动连接的选择；重启后仍退出 |
| 自动模式下咚咚退出、配置不可读或来源账户改变 | 下一次检查清除旧账户与额度；新有效会话重新交换 |
| 平台登录过期 | 自动模式尝试从咚咚重新交换；手动模式等待手动登录 |
| 咚咚会话被拒绝 / 无访问权限 | 等待来源会话改变或用户主动重试；临时网络错误最长每 5 分钟重试 |

自动模式在后台约每 15 秒检查本地会话，额度沿用约 60 秒刷新节奏；本地会话未变化且平台凭据仍有效时不反复换取票据。关闭咚咚进程不等同于注销：连接依据是保存会话是否仍然有效。来源改变检测存在检查间隔，未实测远端踢下线后平台会话的独立有效期。

咚咚配置和安装包保持只读。解密参数从本机安装包提取，代码没有内置实际密钥；仅兼容已识别的集团版 `emc` 3.x 格式，其他格式回退手动登录。原始咚咚会话与临时票据仅在原生内存使用，解密缓冲区和密钥使用 `Zeroizing`；前端只接收账户展示信息、状态和额度。

平台凭据复用系统钥匙串 / Windows 凭据存储。`account.json` 仅保存登录方式和随机会话编号；凭据缓存必须匹配两者，旧缓存即使删除失败也不能在退出或切号后恢复。切换方式、注销和来源变化会使旧请求失效。真实接入代码见 [dongdong.rs](../../rust-desktop/src-tauri/src/dongdong.rs) 和 [account.rs](../../rust-desktop/src-tauri/src/account.rs)。

## Windows 自测

使用 `rust-desktop` 下的构建产物。在已配置好项目构建环境的 Windows 电脑中运行：

```powershell
cd rust-desktop
npm ci
npm run tauri -- build
```

安装包位于 `src-tauri/target/release/bundle/nsis/`（以实际构建日志为准）。默认读取 `%APPDATA%/emc/emc.config.v3.json`；安装目录优先从当前用户 / 本机的卸载注册表项查找，再检查 `%LOCALAPPDATA%`、其 `Programs` 子目录和 `Program Files` 下的常见目录，包含 Squirrel 的 `app-*` 版本目录。

1. 咚咚已登录时启动 EM Use，在“账户与额度”选择“使用咚咚账户”，确认账户和额度正确。已有手动登录的升级用户需要主动选这一次。
2. 选择“手动登录其他账户”，在官方窗口完成其他账户登录；重启 EM Use，确认仍是手动账户。
3. 退出 EM Use 账户并重启，确认自动连接保持暂停；再选择咚咚入口恢复。
4. 自动连接途中改选手动，或关闭尚未完成的手动登录窗口，确认旧请求不会把账户切回去。
5. 自动模式下在咚咚切号 / 退出，等待一次后台检查，确认旧额度清除；手动模式下做同样操作，确认手动账户不被替换。
6. 临时断网后恢复，确认能够重试；找不到配置或不支持的版本应显示原因，手动入口仍可用。

如失败，反馈咚咚版本、安装目录、失败步骤和界面提示即可；不要提供配置文件或任何凭据内容。
